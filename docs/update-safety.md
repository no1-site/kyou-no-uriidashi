# 更新の保護と復旧

## 日次更新の確定順序

1. Windowsの既存スクリプトで `main`・未変更の作業ツリー・未確定の更新がないことを確認し、最新コードを取得する。
2. `.local/update.lock` を排他的に作成する。価格履歴を `.local/update-*` へコピーする。
3. 同じ一時 `products.json` に楽天、Yahoo!、Keepa（後二者は設定時のみ）の順で取得する。楽天が一部APIエラーを記録した場合も全体を停止する。
4. 統合後の各商品のショップ数・送料別件数・対応モール・比較範囲・価格・平均・スコア、全体とカテゴリー別の集計を再計算する。
5. 公開前検証に合格したJSONだけを一時Gitインデックスに登録し、`products.json` だけが変わるコミットを作る。この段階では通常のインデックス・ローカルブランチ・公開用ファイルを変更しない。
6. 強制プッシュを使わずGitHubに送信する。成功後、ローカルの商品ファイル・Gitの状態・価格履歴を確定する。

履歴は従来の楽天・送料込み表示の比較基準を維持する。Yahoo!/Keepaの価格は混ぜず、統合価格の履歴スコアは引き続き無効にする。GitHubへの送信成功を確定条件とし、GitHub Pagesのビルド完了までは監視しない。

## 公開前の停止条件

- 商品数、またはショップ照合済み商品の数が、前回の70%を下回る（必要件数は切り上げ）。11件から7件への減少は停止、8件は通過する。これは原因調査のための運用基準であり、在庫切れ等による正当な減少でも停止する。
- 商品ID・JAN・同一商品内のショップが重複している。
- JANのチェックデジットが不正、出品の照合済みJANと基準JANが不一致、照合根拠やYahoo!の新しい検証版が欠けている。
- 価格が正の整数でない、または1億円を超える。上限は入力異常を検出する運用基準であり、相場を示すものではない。
- 送料区分が不正、送料条件の矛盾を除いた比較対象数と集計・表示価格等が一致しない。

最高価格が最安価格の3倍を超える商品は、価格差の判定を保留し、平均・スコア・履歴比較を消す。送料込みの店が2店以上ならその店同士で判定し、それ以外は全出品を確認する。出品を一部だけ削除して見かけの安さを作らない。

## 失敗・中断時

- API取得・検証の失敗、または送信拒否でリモートが更新前のコミットのままと確認できた場合：旧データと履歴を維持し、一時データとロックを片付ける。原因を解消して通常の更新を再実行できる。
- ネットワーク障害で送信成否が確認できない場合：旧ファイル・旧履歴を維持し、ロックと一時データを残す。通信が戻るまで再送しない。
- 送信成功後にローカル保存が失敗した場合：GitHubの更新を巻き戻さず、未確定の履歴・送信記録・ロックを残す。次回の自動更新は止まる。
- 強制終了や停電の場合：複数ファイルとリモート更新を一つのトランザクションにはできないため、同様にロックを確認して復旧する。履歴の確定前なら前回履歴を維持する。

### 復旧確認

更新プロセスが終了していることを確認してから、`.local/update.lock` の `staging` がこのリポジトリの `.local/update-*` の下であることを確認する。送信開始済みなら、その中の `publication-pending.json` に `base`（更新前）、`commit`（送信対象）、`blob`、`branch` が残る。これらはGitの識別子であり、認証情報は保存しない。

`git ls-remote origin refs/heads/main` でリモート先端を確認する。

- `base` と一致：送信未反映。作業ツリーとインデックスが更新前の状態か確認し、対象の一時データとロックだけを片付けて再実行する。
- `commit` と一致：送信済み。通常の更新を再実行せず、リモートの同コミットへローカルを揃えたうえで、一時履歴を本来の履歴へ確定する。既存の手作業があれば上書きせず先に退避・確認する。
- どちらでもない／通信できない：ロックと一時データを保持し、リモート履歴を調べる。自動でリセット、履歴の確定、ロック削除をしない。

復旧完了後に該当ロックを解除する。現時点では異常中断からの復旧は手動確認が必要。

## 残る制約と100商品へ増やす前の課題

- APIのJANや販売者の記載自体の誤りまでは保証できない。JAN・ブランド・型番・容量・個数を持つ固定の商品台帳と、対象カテゴリーの表記例を増やす。
- Yahoo!の厳格な確認で店舗数が減り得る。理由別の除外集計、実データのレビュー、比較成立率を監視する。
- Keepaは従来のJAN・型番・タイトル照合を維持しており、Yahoo!と同等の数量照合・価格鮮度の強化は今後の課題。有料連携を新しく有効化しない。
- モール統合後の履歴は、楽天だけの履歴と分離した新しい比較基準で設計する。
- APIごとの取得予算・制限に沿った再試行、更新時間とメモリ使用量、20分のタスク上限を検証する。100商品に向けた候補上限や検索件数は今回は変更しない。
- 送信成否不明や異常中断の復旧手順の自動化、通知、GitHub Pages反映確認を検討する。
- `fetch-*.mjs` を単独で本番ファイルに対して実行すると日次更新の一括保護を通らない。通常運用は `run-update-now.cmd` を使い、診断時は出力先を一時ファイルに指定する。
